Wingbreaker is a complete simulated interceptor loop: perception, mission supervision, flight control, a safety veto, an approval gate, and an operator dashboard — launched with one command. Two ROS 2 packages: wingbreaker_interfaces (messages, FlyToGPS, interception service) and wingbreaker_uav (every node, launch, dashboard). Sim assets live in sim/. Weights: yolo26n_DroneDetection.pt at the repo root.

01The problem

Small drones are cheap, quiet, and already inside the fence before anyone looks up. Watching a camera feed is not a defence. A waypoint loop is not a defence. A detector that publishes boxes and then shrugs is not a defence.

The hard part is not “run YOLO.” The hard part is closing the loop from pixel to chase to a deliberate, auditable decision — without coupling the mission brain to PX4, Gazebo, or a particular LLM.

What breaks in the wild

  • Perception stacks that never command the vehicle.
  • Autopilots that fly a box with no idea what they are looking at.
  • Ground stations that require a human to notice, decide, and click in time.
  • Single-link telemetry: when MAVSDK stalls, safety stalls with it.

What this project insists on

  • One launch file brings up sim, flight, vision, and UI.
  • The brain never talks MAVLink. It talks actions and services.
  • Engagement is gated. Default mode is a human on the dashboard.
  • Battery and airborne state can veto a chase independently.

The operational question

An interceptor sitting over a box has four jobs, in order: stay on station, notice a non-cooperative aircraft, get close enough to act, and only then spend the shot. Each job has a different failure mode. Miss the detection and you patrol forever. Detect without a lock and you write a log. Lock without an approval gate and you have built a weapon, not a system. Approve without a report and you cannot tell anyone what happened.

Wingbreaker is the simulation of that full sentence — not a hardware program, not a real interceptor. It is the software spine you would want first: typed interfaces, a supervised flight gateway, a state machine you can read in one sitting, and an operator surface that makes the decision visible.

03The solution

One supervised state machine, a camera that estimates GPS from a bounding box, a flight node that actually arrives, and a fire service that cannot be called until someone — or a policy — approves.

Idleboot ConnPX4 up Patrolbox @ 65 m Lockfly + orbit Decide30 s window Engage/fire Reportaudit row Patrolresume

Denied, timed out, or a failed lock all land in REPORT and cool down for 10 seconds before the next chase. The brain ignores detections while not in PATROL, while airborne is false, and while safe_to_fly is false.

See — detector

Two modes, one message. Live mode loads yolo26n_DroneDetection.pt, strides every third frame, keeps the strongest drone box above 0.35, and publishes only if confidence later clears the brain’s 0.55 chase threshold. Simulated mode (the original bootstrap) drops a synthetic intruder on a timer so the rest of the chain can be tested without weights.

Pixel-to-GPS is deliberately naive: the box centre is a bearing offset through the gimbal’s 114.6° HFOV, then a point assume_range_m (60 m) along that bearing from the vehicle. Altitude is copied from ownship relative altitude. Refine later with depth or target telemetry — do not pretend the current estimate is a tracker.

Go — flight and the gateway

DroneGateway owns one asyncio loop, one MAVSDK System, and a dedicated gRPC port. It reconnects forever. Telemetry (position, battery, armed, landed, heading, NED velocity, GPS) is pumped until the first stream dies, then the whole link is torn down. Callers never see frozen numbers from a dead socket.

Fixed-wing PX4 keeps LandedState UNDEFINED in cruise, so airborne is landed-state OR relative altitude > 3 m. Arrival is 100 m, not “a few metres”: L1 guidance loiters and will not converge like a quadrotor. Goals are cancelable; the brain cancels the current waypoint the instant a valid detection arrives.

Ask — three approval modes

ModeWho decidesWhen to use it

The LLM node is optional and never imported by the base system. Mock policy: approve if detection confidence ≥ 0.85, after a 2 s think delay. OpenAI / Anthropic / Ollama raise NotImplementedError in _ask_llm on purpose — wiring a provider is a contained change, not a rewrite.

04The operator loop

Optional, but this is the piece that makes the system feel real. A supervisor that only logs to a terminal is a lab toy.

web_dashboard is a ROS 2 node with a stdlib ThreadingHTTPServer. No extra web framework. It serves one page, an SSE stream of live state, an MJPEG camera with the detection ROI overlaid, and a POST that calls /request_interception as approver="human".

What the operator sees

  • Mission state, including “AWAITING APPROVAL”.
  • Ownship: pose, heading, speed, battery, sats, airborne.
  • Camera from the gimbal, with the YOLO box drawn on it.
  • Every InterceptReport — detected, intercepted, who signed.
  • A QGC tab if the noVNC bridge is listening on :6080.

What the operator can do

  • Approve or walk away. Timeout is a deny.
  • Keep flying QGC in the same browser if xvfb + x11vnc are installed.
  • Leave the loop entirely: CLI service call still works.
  • Swap the human for the LLM node without touching the brain.

The dashboard is adapted from the pothole-inspection pattern: one process, Server-Sent Events, no websocket library. Clients that fall behind are dropped rather than queued into a memory leak. That is the right trade for a local ops view, not a public site.

QGroundControl-in-browser is deliberately a sidecar (novnc_bridge.py + vendored noVNC), not a ROS node. Core sim does not depend on xvfb. If the operator wants a GCS tab, they launch it. If they do not, nothing is missing from the mission.

05Safety as a second voice

Safety is not a function on the flight node. It is a second MAVSDK connection that can still speak if the primary one is wedged.

flight_node owns udpin://0.0.0.0:14540 and gRPC 50051. safety_node owns :14541 and gRPC 50052. Dedicated ports exist because MAVSDK will otherwise reuse a stale mavsdk_server from the last crashed run and look “connected” while publishing ghosts.

Battery below 20% publishes safe_to_fly = false. The brain will not leave PATROL for a chase. Unknown battery (-1) is treated as safe so a missing telemetry field does not ground a sim that has not yet streamed percent — a pragmatic choice, documented here so nobody mistakes it for a flight-worthiness argument.

Two other gates sit in the brain itself. Detections during takeoff are ignored until connected && airborne. After a report, a cooldown swallows the next 10 seconds of boxes so the same intruder does not immediately re-trigger LOCK. Decision has a 30-second clock. Silence is a deny.

06The world it flies in

The interceptor is a Reaper-styled fixed wing. The target is a scaled X500 that does not run a flight stack. That is a feature.

AssetRole
zam_uav_v2Ownship. IMU, baro, mag, GPS, airspeed plugin, elevons/flaps/rudder, gimbal camera looking along the nose. Lidar removed — this mission is visual.
4031_gz_zam_uav_v2PX4 airframe dropped into ROMFS. Launch sets PX4_SYS_AUTOSTART=4031 and PX4_SIM_MODEL=gz_zam_uav_v2.
intruder_x500Static-flagged, 3× PX4 X500 visual. Spawned and teleported with gz service. No physics, no companion computer.
runway_worldDefault Gazebo world. Patrol waypoints sit on the stock PX4 Zurich spawn box (~47.398 N, 8.546 E).

Intruder modes: flying orbits several copies around the patrol box, static parks them at the orbit start, none leaves the sky empty. PX4 names the first vehicle zam_uav_v2_0, not zam_uav_v2 — the camera bridge topic includes that suffix or the image never arrives.

Launch does not start the app nodes until wait_for_topic has seen an actual sensor_msgs/Image on /camera/image_raw. Checking for a publisher is not enough: ros_gz_bridge advertises immediately, even when Gazebo has nothing to forward. That single gate is why “full stack up” means the camera is alive, not merely that PX4 printed a banner.

Tunables live in one file

wingbreaker_uav/config/uav.yaml — waypoints, patrol altitude, both confidence thresholds, orbit radius (80 m), arrival radius (100 m), approval mode, YOLO path, dashboard port. ROS 2 forbids nested arrays, so waypoints are a flat lat0, lon0, lat1, lon1, … list. Do not nest them.

07Honest limits

A briefing that hides the seams is a brochure. These are the seams.

What is true today

  • End-to-end verified: PATROL → LOCK → human Approve → ENGAGE → REPORT intercepted=True → resume.
  • Live YOLO on the gimbal, not only the simulated detector.
  • Supervised dual MAVSDK gateways that reconnect.
  • Single-command launch with a data-based camera gate.

What is not

  • Engagement is a service stub. There is no seeker, no warhead, no hit geometry.
  • Range is assumed, not measured. A box on the horizon is still “60 m ahead.”
  • The LLM path is a mock policy plus a hook.
  • QGC-in-browser still needs xvfb and x11vnc on the host.

What I would do next

  • A real range. Stereo, depth, or a second view so lock is a track, not a bearing plus a constant.
  • A real provider in _ask_llm. Keep the mock. One live backend, same service, brain still does not know.
  • Multi-intruder arbitration. Hold a track id; drop a stale box instead of always taking the strongest detection.
  • Hardware in the loop. The gateway is the seam — swap SITL for a companion talking MAVSDK and the graph stays.
